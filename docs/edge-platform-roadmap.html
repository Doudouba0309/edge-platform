Implementation roadmap · companion to the proposal

From Design to Deliveries

How the One Base, Many Protocols design gets built, what exists when it is finished, and how a specific site is delivered afterwards — mostly by agents, with humans at the gates that matter.

Tier 1: arm64 + x86_64 · CI builds and smoke-tests every commit

The end state in one sentence

A pinned base image on two architectures, a declarative engine that covers the common protocols by configuration, a conformance suite that makes an adapter's correctness checkable rather than arguable, and an agent harness that turns a register document into a reviewed, deployed, field-ready gateway — without a new image and without anyone guessing a register map.

Part 1 — High-level steps

Five phases. Each one ends in something demonstrable, and the exit test is named so "done" is not a matter of opinion. Sizes are relative effort, not a schedule.

Phase 0 Base image and the two-architecture pipeline largest single phase · partly built already

Make one boring, reproducible image that both Tier 1 architectures build, boot and prove themselves on every commit. Everything later rides on this being trustworthy.

  1. Freeze the northbound contract. Canonical Sample/Batch, published as JSON Schema with a test that fails on drift. exists
  2. Define the base image. Runtime, Greengrass nucleus, provisioning, hardened defaults. Pin the base by digest; generate an SBOM on every build.
  3. Build both architectures. arm64 and x86_64 via buildx; the non-native one under emulation. A failure in either blocks the change.
  4. Define the smoke test precisely — boot; collector reaches ready with a synthetic source; /healthz returns 200; one batch published over mutually authenticated TLS to a local broker on the production topic; clean SIGTERM; measured memory inside the ceiling. the mTLS harness exists
  5. Ship the base component set as Greengrass components: northbound publisher, spool, health, config loader. exists as one process
  6. Make generation deterministic. Locked dependencies, sorted manifests, digest references only — so "regenerate and diff" is a valid review technique.

Exit test: a green pipeline that boots both architectures and moves one schema-valid batch over mutual TLS, on every commit.

Phase 1 The declarative engine medium · highest leverage

Cover the common protocols with configuration instead of code. This is the phase that decides how much agent work is code generation versus filling in a form — and the answer should be "almost none".

  1. Define the point-map schema. One versioned document per source: connection, points, metric name, type, scaling, unit, deadband. The existing OPC UA node list is the seed. partial
  2. Build the engine. Point map in, protocol client driven, Samples out. One code path, so batching, spooling and publishing are never re-implemented per protocol.
  3. Protocol 1 — Modbus TCP. Registers, coils, data types, word and byte order, scaling. This one carries the most real sites.
  4. Protocol 2 — OPC UA. Generalise the existing source onto the engine. partial
  5. Add validation, not just parsing. A command that checks a point map against the device's declared shape and fails loudly before deployment — an out-of-range register or an unknown metric should never reach a gateway.
  6. Test from fixtures, never from hardware. Golden inputs and expected canonical output, checked in.

Exit test: a real site mapped by configuration alone — no new code, no new image, no developer involved.

Phase 2 The adapter kit and the conformance suite medium · the trust boundary

Make "is this adapter correct?" a question a suite answers. Without this, generated adapters are unverifiable, and an unverifiable adapter on a plant floor is worse than none.

  1. Publish the source contract. A small, documented, versioned interface: normalise into Sample, own your own reconnection, never block. exists as an ABC
  2. Surrogate tooling. Generate a simulator from a point map, or replay a captured trace as a fixture. The surrogate is a required deliverable, not a convenience.
  3. Fix the fixture format. Known input, expected canonical output, and the reason it is expected to look like that.
  4. Build the conformance suite: schema conformance; scaling round-trip; word and byte order against a golden fixture; signedness and bounds; timestamp sanity; quality propagation; kill-the-surrogate and prove no loss; resource ceiling on the smallest target; determinism.
  5. Produce a conformance report as a machine-readable artifact, attached to every change. A human reads the report, not the code.
  6. Prove the kit by adding a third protocol as a code adapter and passing the whole suite.

Exit test: a code adapter for a genuinely custom protocol passes the full suite, and the report is attached to the change.

Phase 3 The agent factory medium · where the speed comes from

Turn the repeatable part of delivery over to agents, with structure that makes wrong output detectable rather than merely unlikely.

  1. Write skills as procedures, each ending in a verification command. A skill without one is a liability. Version skills in the repository and contract-test them like code.
  2. Define the context layers and the rule for loading them: invariant (the contract) → reusable (adapter kit, protocol playbooks) → site (register map, captures) → this task. Never inject the whole repository.
  3. Store memory as data, not prose. Site facts with an owner, an expiry and the evidence that produced them. Technique lives in skills. Credentials never live here at all.
  4. Define subagents by artifact contract: input, output artifact, verification command, and the condition under which they must refuse. "No capture and no simulator" must produce a refusal, not an invented register map.
  5. Expose the new operations to agents over the existing MCP surface: validate a point map, build a surrogate, run conformance, open a change.
  6. Record provenance. Every published artifact names the base digest, the skill versions and the run that produced it — without which a generated deployment cannot be audited or rebuilt.

Exit test: one deployment delivered end to end by an agent, reviewed and merged by a human, with a conformance report and a resource budget.

Phase 4 Fleet operations ongoing

The phase that decides whether the platform survives year two: patching, rollout and knowing which sites run what.

  1. Rollout and rollback policy. Roll back on failure, cap the rollout rate, abort automatically past a failure threshold. in the deploy script
  2. Patch cadence. One base-image rebuild propagates an OS or runtime fix fleet-wide as a component update; only hardware and firmware force a new image.
  3. A provenance ledger with the one query that matters: which sites run which digest, and which skills produced their adapters.
  4. Field signals. Decide which indicators mean "this adapter is wrong" — a metric that stopped arriving, a quality that never leaves bad, a value pinned at a bound, a reconnect rate that keeps climbing.

Exit test: one base-image security fix shipped to the whole fleet through a single rebuild and one deployment.

Part 3 — Delivering a specific site, afterwards

The pipeline, once it is running

  1. IntakeSite, hardware, protocol, tag list, plus the register document or a capture.
  2. DecideDoes a declarative map cover it? Prefer yes; escalate to code only if not.
  3. SurrogateBuild a simulator from the map, or replay the capture.
  4. ConformRun the suite. Produce the report. Refuse on any failure.
  5. ProposeOpen a change: adapter, fixture, report, budget. Regenerate and diff.
  6. ReviewHuman reads the diff, the report and the numbers. Merges.
  7. BuildCI: both architectures, SBOM, smoke test, publish by digest.
  8. Roll outDeployment to the site's thing group, watching for rollback.
  9. OperateWrites to a PLC need a signature. Telemetry may be autonomous.

What the agent may never do

Hard limits, regardless of confidence

  • Invent a register map. A mapping originates from a vendor document, a captured trace, or a human engineer. A model can produce a completely plausible map that is wrong in one field, and nothing downstream will complain — the numbers look fine.
  • Write to a PLC. Setpoints, commands and mode changes need a human decision. Reading telemetry can be autonomous; changing the process cannot.
  • Touch credentials. Provisioning uses short-lived identities and fleet provisioning. An agent never handles a long-lived private key, and no key is baked into an image.
  • Ship without a surrogate and a passing report. No exceptions, including for "obvious" protocols.
  • Publish a component version twice. Versions are immutable; the fix is always a new version.

One caveat about the AWS-dependent parts

Nothing in this repository has been executed against a real AWS account. The provisioning, publishing and deployment scripts are written, syntax-checked and dry-run capable, and the cross-artifact consistency between them and the collector is now covered by tests — but the cloud-side behaviour itself is unverified. Treat the AWS column of this roadmap as designed, not proven, until one real provisioning run has happened.

Sequencing advice

If you only do two things

1. Finish Phase 0 properly — two architectures, a precise smoke test, digest pinning. It is unglamorous and it is the foundation every later phase assumes.

2. Build the conformance suite before generating any adapters. Generation is cheap and verification is not, and the order matters: a suite written after the first generated adapters will be shaped around them instead of around correctness.

Phase 1 can run in parallel with Phase 0 once the image exists, and Phase 3 should not start until Phase 2 can tell an agent "no" — a factory without a quality gate produces confident, unverifiable firmware.
