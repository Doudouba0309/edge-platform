Hardware architecture: from sunlight to AWS

The gateway is not a mysterious box. It is a small industrial computer in a cabinet, with power, storage, serial ports, network ports and a secure identity. This chapter explains the physical chain around it and the choices that make it survive a real solar site.

The one-sentence version. Sensors and inverters produce electrical signals; PLCs, meters and gateways turn those signals into data; the edge gateway translates and protects the data; the network carries it outbound; AWS receives it.

4. Power, grounding and survival

A gateway that loses power mid-write can corrupt its filesystem. A gateway that shares a noisy ground with a inverter can reset randomly. These are not software problems.

  • Use a proper supply. Respect the input voltage range and fuse the feed.
  • Use a UPS or supercapacitor. Give the gateway time to flush and shut down.
  • Ground and surge-protect. Follow the site’s electrical rules; do not improvise.
  • Separate noisy cables. Keep RS-485 away from motor and inverter power cables where possible.
  • Use isolation. An isolated RS-485 port protects the gateway from ground differences.
  • Test power loss. Pull the power and confirm the spool survives a clean restart.

5. Serial wiring: RS-485 in practice

RS-485 is a shared bus. Several devices can sit on one pair of wires, but only one should talk at a time. The gateway is usually the master.

  • Daisy chain, not star. Keep stubs short.
  • Terminate both physical ends. Usually 120 Ω; not at every device.
  • Bias the idle line if the vendor requires it.
  • Match baud, parity, data bits and stop bits. 9600 8N1 is common but not universal.
  • A/B labels are inconsistent. Swapping A and B is a valid first test.
  • Use one slave id per device. Duplicate ids cause collisions and timeouts.

The preferred design is outbound-only. The gateway opens a TLS connection to AWS; nothing on the internet opens a connection into the plant. The site firewall should allow outbound DNS, NTP, HTTPS (443) and MQTT/TLS (8883), and should not expose the gateway to inbound traffic.

7. Sizing the gateway

The design target is a device with about 1 GB of RAM and a modest CPU. The queue is bounded; the spool is byte-budgeted. But storage still needs arithmetic.

A worked example. Suppose a site publishes 12 points every 10 seconds and a batch is about 2.5 KB. That is roughly 6 batches/minute, 360/hour, about 21.6 MB/day. A 64 MB spool would hold only about three days at that rate. A 30-day buffer would need roughly 650 MB, plus SQLite overhead and logs. The current 64 MB test default is a test budget, not a 30-day field guarantee.

The SOW asks for 30–90 days of local buffering. That is a site sizing decision: choose storage and spool.max_bytes together. Do not assume the default is enough for a real 30-day outage.

For a pilot, an industrial box with two Ethernet ports, an isolated RS-485 port, a wide-input power supply and a DIN-rail mount is the safer choice. The test core on this laptop is not a production hardware recommendation.

9. Installation checklist

  • Cabinet space, DIN rail and ventilation confirmed.
  • Power supply within range; fuse and surge protection fitted.
  • UPS or graceful shutdown available.
  • RS-485 A/B, ground, shield, termination and bias checked.
  • Ethernet ports labelled OT and WAN; no accidental bridging.
  • Outbound DNS, NTP, 443 and 8883 allowed; no inbound rule.
  • Time zone and NTP configured.
  • Gateway identity and certificate installed.
  • Spool size and retention agreed with the client.
  • Support bundle and logs reachable for support.
  • Power-loss and network-loss tests repeated on the real box.

11. Hardware and security

  • No inbound shell by default. The support model is logs, support bundle and deployment.
  • No AWS keys on disk. The nucleus owns the certificate and exchanges it for temporary credentials.
  • Protect the private key. Restrict file permissions; never copy it into the repository.
  • Lock the cabinet. Physical access to the gateway is access to the site identity.
  • Plan rotation. Certificates and credentials have a lifecycle; record the owner.
  • Use the client’s account and keys. The current sandbox is not a client deployment.

12. What this means for the first pilot

For the first solar + Modbus TCP pilot, the minimum hardware is:

  • One industrial gateway with Linux, Python 3.12 and two Ethernet ports.
  • One isolated RS-485 port if RTU is included later.
  • One inverter with a documented Modbus TCP map.
  • One weather station or revenue meter, with its protocol and map.
  • A site firewall rule that allows outbound 443/8883 and no inbound access.
  • A UPS or clean-shutdown plan.
  • A storage budget that matches 30–90 days, not the 64 MB test default.
