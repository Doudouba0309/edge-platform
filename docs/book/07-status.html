What is still live

The sandbox was intentionally left running after the proof so it could be inspected:

  • the local edge-platform-aws-core container and its volume;
  • the thing edge-platform-sandbox-core and its thing group;
  • the core certificate and IoT policy;
  • the TES role and role alias;
  • the observer certificate and policy;
  • component versions and deployment history;
  • the component ZIP and other objects in the S3 bucket.
Teardown is a separate action. It is destructive and has not been performed. Never delete a certificate still attached to a live core without planning the order. The exact cleanup order is in Part 5, step 13.

The roadmap, in plain terms

The project’s own roadmap defines five phases. Only the first is substantially complete; the next three are the product.

PhaseWhat it deliversState
0 — Base and pipelineFrozen contract, image, two-architecture CI, spool, health, nucleus, component package.Mostly done
1 — Declarative enginePoint-map schema, Modbus TCP, OPC UA, validation before deployment.Next
2 — Adapter kit and conformanceSource contract, surrogates, fixtures and a machine-readable conformance report.Not started
3 — Agent factorySkills, context layers, subagent contracts, provenance.Not started
4 — Fleet operationsRollout, rollback, patch cadence, provenance ledger and field signals.Not started

Recommended next step

Finish the base, then make it useful on a factory floor. The next build task should be the declarative point-map engine and the Modbus TCP source, with a surrogate and fixtures. That is the shortest path from “pretend sensor” to “a controls engineer can map a real PLC without writing code”.

Before Phase 1

  1. Decide whether to keep or tear down the live sandbox.
  2. If it will be recreated, add the repeatable AWS provision/publish/deploy/teardown scripts and runbook.
  3. Keep the validation runbook green as the code changes.

Then Phase 1

  1. Define the versioned point-map schema.
  2. Build the engine: point map in, protocol client driven, Samples out.
  3. Add Modbus TCP: registers, coils, data types, word/byte order, scaling.
  4. Generalise OPC UA onto the same engine.
  5. Add point-map validation before deployment.
  6. Test from fixtures and a surrogate, never from a live PLC.

What success will look like next

Not “another AWS message”. The next real milestone is:

A controls engineer writes one point-map file for a simulated Modbus or OPC UA device, deploys the collector without changing the image or writing Python, and a schema-valid batch appears in AWS.

At that point the platform has crossed from “the pipe works” to “a site can use it”.

Honest bottom line

QuestionAnswer
Can it send real telemetry to AWS?Yes, proven with a synthetic source and a real Greengrass core.
