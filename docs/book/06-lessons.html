Part 6

The real failures, and what they taught us

This part is deliberately uncomfortable. Every error below actually happened while building the AWS proof. The fix matters, but the lesson matters more.

General rule. When the component is “running” but nothing arrives, the problem is usually one of three things: the wrong identity, the wrong permission, or the wrong endpoint. The log message often names a different layer than the one that is broken.

The failure log

1. A docs-only change took five minutes

Symptom: editing an HTML or README file triggered full image and nucleus builds.

Cause: the workflow had no path filter, and GitHub runners did not keep Docker layers between runs.

Fix: skip the pipeline for docs-only changes and use a buildx GHA cache for image layers.

Lesson: a “small” documentation change is only cheap if CI agrees. Cache and path rules are part of developer experience, not optional polish.

2. IAM user sign-in asked for an account id

Symptom: after creating edge-platform-admin, the sign-in page wanted a 12-digit account id.

Cause: an IAM user signs in to a specific account; the account id (or an account alias) is the address.

Fix: copy the account id from the root console’s top-right menu before signing out, or use Forgot account ID? with the root email. An account alias makes the URL easier.

Lesson: the IAM user creation page does not create a separate sign-in address. Save the account id first.

3. The wheelhouse contained awsiotsdk, but the component did not install it

Symptom: the component installed and started, but the Greengrass sink could not import the AWS IoT SDK.

Cause: the recipe installed edge-collector, not edge-collector[aws]. The wheel was in the wheelhouse, but pip had no reason to install the optional extra.

Fix: install edge-collector[aws] in the recipe.

Lesson: a dependency being present in an artifact does not mean it is installed. Optional extras are opt-in.

4. The component was deployable but never matched the core

Symptom: deployment failed with no available component version.

Cause: the recipe used architecture: arm64; the core reports aarch64.

Fix: use aarch64 and amd64 in the recipe manifests.

Lesson: platform names are exact strings, not marketing names. A pure-Python artifact is not exempt from the platform match rule.

5. “Certificate is invalid on this endpoint”

Symptom: the core connected to IoT Core and reported healthy, but the token exchange returned 403 “Certificate is invalid on this endpoint”.

Cause: the credentials endpoint was derived from the data endpoint prefix. It is a different endpoint with a different hostname.

Fix: call aws iot describe-endpoint --endpoint-type iot:CredentialProvider and use that value.

Lesson: the data endpoint and the credentials endpoint are two different services. Never guess one from the other.

6. TES returned 403 “Access Denied”

Symptom: the credentials endpoint was now correct, but the core still could not get temporary credentials.

Cause: the certificate’s IoT policy did not grant iot:AssumeRoleWithCertificate on the role alias.

Fix: add that permission with the role alias ARN as the resource.

Lesson: the role trust policy and the certificate policy are separate. The role can trust the credentials service and still be unusable if the certificate is not allowed to ask for it.

7. Artifact download returned 403

Symptom: the deployment reached S3, then failed with “GetBucketLocation returns 403 Access Denied”.

Cause: the TES inline policy allowed s3:GetObject on bucket/*, but not s3:GetBucketLocation on the bucket itself.

Fix: add both actions and include both the bucket ARN and the object ARN.

Lesson: S3 permissions are not uniform across bucket-level and object-level actions. The error names the missing action if you read the nested cause.

8. IPC publish was not authorized

Symptom: the component connected to the nucleus socket, then logged “Not Authorized” on every batch.

Cause: the recipe’s access-control operation or resource did not match the actual IPC call. An old invalid policy in the nucleus package store also kept blocking authorization after a new version was installed.

Fix: use the registered operation aws.greengrass#PublishToIoTCore and a matching topic resource (edge/+/+/telemetry). If an older recipe was invalid, start with a clean core root so only the valid recipe is loaded.

Lesson: “component running” is not “component allowed to publish”. Read the nucleus authorization log, not only the component log. Immutable versions plus a stale local package store can hide a correct recipe.

9. The local collector would not start

Symptom: Errno 48: address already in use on port 8081 during validation.

Cause: an earlier collector process was still running.

Fix: find it with lsof -nP -iTCP:8081 -sTCP:LISTEN, stop that process, and rerun. The validation was repeated cleanly.

Lesson: a failed local test can be an environment problem, not a code problem. Clean up stray processes before drawing conclusions.

How to read the logs

QuestionWhere to look
Is the core container running?docker ps | grep edge-platform-aws-core
Did the nucleus start?docker logs --tail 50 edge-platform-aws-core — look for Launched Nucleus successfully.
What is the nucleus doing?docker exec edge-platform-aws-core tail -100 /greengrass/v2/logs/greengrass.log
What is the collector doing?docker exec edge-platform-aws-core tail -100 /greengrass/v2/logs/io.github.doudouba0309.EdgePlatform.Collector.log
Did the deployment succeed?aws greengrassv2 list-installed-components --core-device-thing-name edge-platform-sandbox-core --region ap-southeast-1 --profile edge-platform-admin
Is the core healthy?aws greengrassv2 list-core-devices --region ap-southeast-1 --profile edge-platform-admin
Is the data arriving?AWS IoT MQTT test client, subscribe to edge/#.

Lessons worth carrying forward

  1. Use exact names. aarch64 is not arm64; iot:CredentialProvider is not the data endpoint.
  2. Permissions are layered. IoT policy, role trust, role policy and component IPC access are four different gates.
  3. “Running” is not “working”. A process can start, connect to IPC and still be denied every publish.
  4. Read the whole error chain. The top-level message often says “download failed”; the nested cause names the exact missing permission.
  5. Versions are immutable. Bump; never overwrite. A stale invalid recipe can poison a clean-looking deployment.
  6. Clean state is a tool. When a core has accumulated invalid component recipes, a fresh root is faster than arguing with the cache.
  7. Test offline first. The image, collector, mTLS and replay tests catch most code problems before AWS enters the picture.
