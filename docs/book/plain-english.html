What this is, in ordinary language

This page explains the whole project without assuming you know what a PLC, a register, a Greengrass component or a spool is. You do not need to run anything. Read it like a short story about a solar site, a small computer, and a parcel of readings.

The shortest possible version. A solar site produces useful measurements. Those measurements are trapped in equipment that speaks many different languages. We built a small, reliable computer program that reads them, turns them into one common parcel, keeps the parcel safe when the internet is down, and sends it to AWS when the connection returns.

1. The problem: the solar site knows a lot, but cannot tell us

Picture a solar plant on a sunny morning. Inverters are turning sunlight into electricity. A weather station is measuring how bright the sun is. A revenue meter is recording how much power leaves the site. Somewhere, a SCADA system or a historian is already collecting much of this information.

The trouble is that every piece of equipment describes itself differently. One inverter might use Modbus TCP. Another speaks OPC UA. A weather station may use MQTT. Each vendor uses different names, different units, different address numbers and different rules. A reading that means “AC power” in one device might sit at a completely different address in another.

The people who run the site want simple questions answered: How much power are we making? Is an inverter underperforming? Is a fault code appearing? How does today compare with the weather forecast? The people who protect the plant do not want the cloud reaching directly into the control network. And the internet connection is not perfect. It can disappear for minutes, hours or longer.

2. The idea: put a small translator at the edge

“The edge” simply means the place near the equipment — at the solar site, not in a distant data centre. We put a small, dependable computer there.

It listens

It asks the inverter, meter and weather station for their readings using the languages they already speak.

It translates

It turns every reading into one common shape, so the cloud does not need a different rule for every vendor.

It protects

If the internet is down, it keeps the readings on local disk instead of losing them.

It sends

When the connection returns, it sends the backlog and new readings to AWS in a safe order.

Think of it as four workers in one small box: a translator, a packer, an outbox clerk and a sender. The box is small on purpose. It may have only 1 GB of memory, so it must not try to be a data centre.

3. The one common parcel: a Sample and a Batch

The most important idea in the project is that all those different languages must end up in one common shape.

A Sample is one reading. It answers:

  • Which asset is this? (for example, inverter inv-01)
  • What is being measured? (for example, ac_power_kw)
  • What is the value? (for example, 123.4)
  • When was it measured? (always in UTC, so sites in different time zones agree)
  • Where did it come from? (a register, an OPC UA node, a topic)
  • What unit is it in? (kW, °C, kWh)
  • Can we trust it? (good, uncertain, bad or stale)

A Batch is a small parcel of samples from one device. Sending one parcel instead of one message per reading saves money and reduces network chatter. It is like posting a folder of letters instead of one envelope per page.

Why “frozen”? If every protocol invented its own parcel shape, every dashboard and database would need a special case. We freeze one shape — like agreeing that every parcel in the postal system has the same label layout. A future change to the shape must be deliberate and versioned, not accidental.

4. The point map: the address book

A point map is a configuration file that says, in effect:

“On inverter inv-01, the value at holding register 100 is AC power, stored as a 32-bit decimal number, in kW. Call it ac_power_kw. Ignore changes smaller than 0.1 kW.”

The point map is the address book between the equipment and the common parcel. It is deliberately a file, not Python code, because a controls engineer should be able to review it. It also records the awkward details: register type, word order, scaling and units.

The point map does not guess. A real register map must come from a vendor document or a captured trace. A wrong address can produce a plausible number for the wrong measurement, which is worse than no number.

5. What happens when the internet disappears?

Imagine the site link goes down at 10:00 and returns at 14:00.

  1. The collector keeps reading the equipment.
  2. The sender cannot reach AWS, so it says “not available”.
  3. The batch goes into a local spool — an outbox on disk.
  4. New batches queue behind the old ones. Nothing overtakes the backlog.
  5. At 14:00 the link returns. The oldest parcel is sent first, then the next, and so on.
  6. Only after a parcel is confirmed sent is it removed from the outbox.

This is called store-and-forward. It is the difference between “we lost four hours of data” and “we have four hours of data with a delay”.

If the process crashes or the power cuts, a committed spool entry survives. The collector may send a parcel twice after a crash — that is safer than silently losing it. The central system must be able to ignore duplicates.

6. The queue and the spool are different things

QueueSpool
WhereMemory (RAM)Local disk (SQLite)
SizeSmall and boundedLarger, byte-budgeted
Survives power cut?NoYes, for committed entries
JobAbsorb short burstsSurvive long outages
When fullDrop oldest by defaultDrop oldest payloads over budget

The queue is a shop counter. The spool is the back room. If the counter is full, the oldest item on the counter is removed to make room for the newest; that policy is called drop_oldest. The back room is larger and survives a power cut.

7. Why a “postmaster” sits between us and AWS

The collector does not hold AWS passwords or private keys, and it does not talk to AWS directly. A local Greengrass process — the nucleus — owns the device certificate and the secure connection. It is the local postmaster.

  • The collector hands a sealed parcel to the postmaster over a local socket.
  • The postmaster owns the identity and the encrypted connection to AWS.
  • The postmaster can queue messages while the cloud link is down.
  • The collector never contains long-lived AWS keys.

This is why the component can be installed, updated and removed without handling the site’s cloud identity.

8. What is actually working today

The project has reached a real, tested milestone:

  • A collector can read a solar-style Modbus TCP device.
  • It turns the readings into the common Sample/Batch shape.
  • It batches and buffers them.
  • It sends them through Greengrass to AWS IoT Core.
  • A real Modbus batch has been observed in AWS.
  • Status heartbeats, JSON logs, a support bundle, CloudWatch logs and a heartbeat alarm are working.
  • The same code builds and passes tests on arm64 and x86_64.

The current live component is 1.0.12. The solar data comes from a local surrogate, not a real inverter yet. The surrogate is a stand-in that behaves like a small solar device so the whole path can be tested safely.

9. What is not done yet

  • A real inverter on a real site. We need the Huawei model and its register map.
  • Modbus RTU. RS-485 wiring and a USB adapter, then hardware-in-the-loop testing.
  • OPC UA. The next protocol adapter.
  • A production base image. The test core is 601 MB; the production target is smaller.
  • The client’s AWS account, Git organization and namespace. The current names are sandbox placeholders.
  • A remote shell. This is deliberately absent. Support is evidence-first: logs, bundle and alarm.
  • Forty sites. We are proving one solar site and one protocol first.

10. What the cloud currently receives

AWS IoT Core receives two kinds of messages:

  • Telemetry on edge/<gateway>/<device>/telemetry. These are the readings.
  • Status on edge/<gateway>/status. This is a heartbeat saying “I am alive, ready and connected”.

IoT Core is a mailbox, not a filing cabinet. It passes messages to subscribers; it does not keep the telemetry forever. S3 currently stores component ZIPs and support bundles, not telemetry. A future IoT rule can copy telemetry to S3 if the client wants a permanent archive.

11. Why there is so much testing

A gateway that works for five minutes in a demo is not a gateway. The tests deliberately break things:

  • Stop the broker and check that data is spooled, then replayed.
  • Restart the process and check that the spool survives.
  • Corrupt a spooled parcel and check that the rest continues.
  • Send an invalid point map and check that it fails before deployment.
  • Disconnect the gateway and check that the heartbeat alarm fires.
  • Run on both arm64 and x86_64.

The goal is not to make the tests look impressive. It is to find the failure before the client’s site does.

12. What you need to do now

  1. Nothing urgent. The current sandbox is running and the SNS alarm is confirmed.
  2. For a real site, provide the inverter model and register map.
  3. For RTU, provide a gateway, USB-RS485 adapter and a sensor/PLC for a bench test.
  4. Before client deployment, provide the client Git organization, AWS account and namespace.
  5. Before a pilot, approve data retention, remote access and security review.
