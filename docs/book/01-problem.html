Part 1

The problem: solar data is trapped

A solar plant already knows a great deal about itself. The trouble is getting that knowledge out of the site reliably, cheaply and without opening a hole in the plant network.

The SOW covers 40 renewable-energy sites. This handbook starts with one solar site and one protocol — Modbus TCP — because that is the shortest path to a real inverter reading. The full first-slice scope is in Solar + Modbus TCP Scope.

Start with a real solar site

Picture a solar plant. Inverters turn DC from the arrays into AC for the grid. A weather station reports irradiance, ambient temperature and wind. A revenue meter records export and import. A SCADA system or historian already collects much of this, often through a programmable logic controller (PLC).

The equipment is not uniform. One inverter exposes Modbus TCP registers; another speaks OPC UA; a gateway may publish MQTT. Vendors such as Huawei use different names, units, register layouts and quirks. The useful measurements are concrete: AC and DC power, energy yield, voltage, current, frequency, temperature, operating state and fault codes.

The people who run the site want generation, availability, capacity factor and inverter health in the cloud. The people who protect the plant do not want the cloud to reach directly into the control network. And the network itself is not perfect: cellular drops, firewalls reboot, switches get unplugged, and maintenance windows happen.

The central idea. Put a small, dependable computer at the edge of the solar site. Let it speak the local protocols, translate everything into one shape, hold on to data when the uplink is down, and send it north to AWS when it can.

Why not send every reading straight to AWS?

Three practical reasons:

  1. Cost. AWS IoT Core charges per message. Sending one message per sensor reading is wasteful when you can send one carefully packed batch.
  2. Reliability. A site link can disappear for minutes or hours. If the gateway does not buffer, the data is simply gone.
  3. Security and control. The cloud should not need a route into the plant control network. The gateway makes the outbound connection; nothing needs to connect inward.

The gateway is therefore a translator, packer, outbox and sender, not a miniature data centre.

The four jobs of the edge gateway

1. Speak local protocols

Read from inverters, meters, weather stations and PLCs using whatever they already speak. This is called the southbound side.

2. Normalise

Turn every reading into the same small record: device, metric, value, time, quality and origin.

3. Pack and protect

Group readings into batches, keep a bounded queue in memory, and write to a disk outbox when the uplink is down.

4. Send north

Deliver to AWS through the Greengrass nucleus, which owns the certificate and the secure connection.

The constraints that shaped everything

The design is not arbitrary. It follows from a small number of hard constraints:

ConstraintConsequence
A gateway may have as little as 1 GB of RAM.No web framework, no unbounded queue, no heavy runtime. The queue and spool have explicit budgets.
The uplink is intermittent.Store-and-forward is mandatory. Ordering must be preserved: once anything is in the outbox, new batches queue behind it.
Two processor families must be supported.Tier 1 is arm64 and x86_64. Both are built and smoke-tested.
Devices may be untouched for years.Few dependencies, a health endpoint with no framework, and an image with a pinned base.
One image should serve many sites.The image is generic. Site-specific protocol work belongs in a component or configuration, not in a new image.
The cloud must not hold the site’s keys.The component never stores AWS credentials. The nucleus owns the certificate and the connection.
Data must stay understandable.One frozen wire format, one topic scheme and a schema that tests can defend.

Why a “frozen” data contract matters

Imagine every department inventing its own parcel shape. The mailroom would need a different sorting machine for each one. In the same way, if OPC UA data had one JSON shape and Modbus data another, every downstream dashboard, rule and database would need special cases.

So the project freezes a single shape called Sample, and a group of samples called a Batch. Until that shape is deliberately changed and versioned, every protocol must fit into it. This is the single most important design decision in the project.

What “done” means at this stage

The project is built in layers, and each layer has a testable finish line:

  • A developer can install the project and run its checks.
  • A collector can read a synthetic source, batch readings and log them.
  • The same collector can publish over mutual TLS and survive an outage.
  • An image can boot on both Tier 1 architectures and pass a smoke test.
  • A Greengrass component can be built, published and deployed.
  • A real message can be observed in AWS IoT Core.

All six are now true. What is not yet true is the solar-site part: reading a real inverter over Modbus TCP, then adding OPC UA and RTU. That is the next phase, not a hidden part of this one.

Do not confuse the proof with production. The current source is a deterministic pretend sensor. The AWS account is a sandbox. The component is a real deployment, but no real inverter has been connected, and no production security review has happened.
