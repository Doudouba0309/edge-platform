Part 5

Rebuild the AWS proof

This is the advanced part. It creates real AWS resources, runs a Greengrass core, publishes the component and verifies a message in IoT Core. Do it only in a dedicated sandbox account.

This part mutates AWS. It creates a thing, certificate, policies, IAM role and billable resources. Use a disposable sandbox account, never production. The current manual steps are the exact sequence used for the proof; a one-command provisioning script is still a future improvement.

1. Start with the account

If the account does not exist yet, follow the separate AWS Sandbox Setup guide first. At a minimum you need:

  • A dedicated, non-production AWS account.
  • MFA on root and no root access keys.
  • A small budget alarm.
  • A named admin identity with MFA — the proof used edge-platform-admin.
  • AWS CLI v2 configured with that profile.
  • Region ap-southeast-1.
  • One private S3 bucket.

Check the identity and region before doing anything else:

aws sts get-caller-identity --profile edge-platform-admin
aws configure get region --profile edge-platform-admin
Expected. The account id and an edge-platform-admin ARN; region ap-southeast-1.

2. Set the shell variables

The commands below use variables so that no account id or secret is pasted into the document. Run these in the same terminal: 

PROFILE=edge-platform-admin
REGION=ap-southeast-1
ACCOUNT_ID="$(aws sts get-caller-identity --profile "$PROFILE" --query Account --output text)"
THING=edge-platform-sandbox-core
GROUP=edge-platform-sandbox
POLICY=edge-platform-sandbox-core-policy
ROLE=edge-platform-sandbox-TESRole
ROLE_ALIAS=edge-platform-sandbox-TESRoleAlias
BUCKET="edge-platform-sandbox-${ACCOUNT_ID}-${REGION}"
COMPONENT=io.github.doudouba0309.EdgePlatform.Collector
VERSION=1.0.5

echo "$ACCOUNT_ID" "$BUCKET"

Create the bucket only if it does not exist. If it already exists, skip this command:

aws s3api create-bucket \
  --bucket "$BUCKET" \
  --region "$REGION" \
  --create-bucket-configuration LocationConstraint="$REGION" \
  --profile "$PROFILE"

aws s3api put-public-access-block \
  --bucket "$BUCKET" \
  --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile "$PROFILE"

3. Create the thing and group

aws iot create-thing --thing-name "$THING" --profile "$PROFILE"

aws iot create-thing-group --thing-group-name "$GROUP" --profile "$PROFILE"

aws iot add-thing-to-thing-group \
  --thing-name "$THING" --thing-group-name "$GROUP" --profile "$PROFILE"

The thing is the cloud record of this gateway. The thing group is a convenient way to target deployments.

4. Create the device certificate and root CA

mkdir -p certs/sandbox

curl -fsSL https://www.amazontrust.com/repository/AmazonRootCA1.pem \
  -o certs/sandbox/AmazonRootCA1.pem

aws iot create-keys-and-certificate --set-as-active \
  --certificate-pem-outfile certs/sandbox/cert.pem \
  --private-key-outfile certs/sandbox/private.key \
  --public-key-outfile certs/sandbox/public.key \
  --profile "$PROFILE"

The output contains the certificate ARN. Save it in a shell variable: 

CERT_ARN=arn:aws:iot:${REGION}:${ACCOUNT_ID}:cert/<the-id-from-the-output>

The private key is a secret. It belongs in certs/, which is git-ignored. Never paste it into a document or a chat.

5. Create the core IoT policy

The policy is not just MQTT. The core must also call the Greengrass control plane and assume its token exchange role. The repository template is deploy/aws/iot-policy.json.tmpl; the build script renders it with the account, region, thing and role alias. 

GG_BUCKET="$BUCKET" \
GG_ACCOUNT_ID="$ACCOUNT_ID" \
GG_THING_NAME="$THING" \
GG_ROLE_ALIAS="$ROLE_ALIAS" \
make component

Then create and attach the policy:

aws iot create-policy \
  --policy-name "$POLICY" \
  --policy-document file://build/component/iot-policy.json \
  --profile "$PROFILE"

aws iot attach-policy \
  --policy-name "$POLICY" --target "$CERT_ARN" --profile "$PROFILE"

aws iot attach-thing-principal \
  --thing-name "$THING" --principal "$CERT_ARN" --profile "$PROFILE"
Three permission families are required. MQTT for telemetry, Greengrass control-plane calls for deployments, and iot:AssumeRoleWithCertificate for the role alias. Missing any one produces a different, confusing error.

6. Create the token exchange role

The nucleus does not store AWS access keys. It asks AWS IoT for temporary credentials by presenting its certificate and a role alias. That role is called the token exchange role, or TES role. 

cat > certs/sandbox/trust.json <<'JSON'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {"Service": "credentials.iot.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }
  ]
}
JSON

aws iam create-role \
  --role-name "$ROLE" \
  --assume-role-policy-document file://certs/sandbox/trust.json \
  --profile "$PROFILE"

Create an inline policy with the permissions the core needs:

cat > certs/sandbox/tes-policy.json <<JSON
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["iot:Publish", "iot:Receive"],
      "Resource": ["arn:aws:iot:${REGION}:${ACCOUNT_ID}:topic/\$aws/things/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iot:Subscribe"],
      "Resource": ["arn:aws:iot:${REGION}:${ACCOUNT_ID}:topicfilter/\$aws/things/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iot:Connect"],
      "Resource": ["arn:aws:iot:${REGION}:${ACCOUNT_ID}:client/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iot:GetThingShadow", "iot:UpdateThingShadow", "iot:DeleteThingShadow"],
      "Resource": ["arn:aws:iot:${REGION}:${ACCOUNT_ID}:thing/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": ["arn:aws:logs:${REGION}:${ACCOUNT_ID}:log-group:/aws/greengrass/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetBucketLocation"],
      "Resource": [
        "arn:aws:s3:::${BUCKET}",
        "arn:aws:s3:::${BUCKET}/*"
      ]
    }
  ]
}
JSON

aws iam put-role-policy \
  --role-name "$ROLE" \
  --policy-name GreengrassV2TokenExchangeRoleAccess \
  --policy-document file://certs/sandbox/tes-policy.json \
  --profile "$PROFILE"

Create the role alias that the nucleus asks for:

aws iot create-role-alias \
  --role-alias "$ROLE_ALIAS" \
  --role-arn "arn:aws:iam::${ACCOUNT_ID}:role/${ROLE}" \
  --credential-duration-seconds 3600 \
  --profile "$PROFILE"
Why both a bucket ARN and a bucket/* resource? s3:GetBucketLocation applies to the bucket itself; s3:GetObject applies to the object. Using only the object path produced a 403 during the proof.

7. Get the two IoT endpoints

The data endpoint and the credentials endpoint are different hostnames. Do not derive one from the other. 

DATA_ENDPOINT="$(aws iot describe-endpoint \
  --endpoint-type iot:Data-ATS --region "$REGION" --profile "$PROFILE" \
  --query endpointAddress --output text)"

CRED_ENDPOINT="$(aws iot describe-endpoint \
  --endpoint-type iot:CredentialProvider --region "$REGION" --profile "$PROFILE" \
  --query endpointAddress --output text)"

echo "$DATA_ENDPOINT"
echo "$CRED_ENDPOINT"

The data endpoint looks like xxxxx-ats.iot.ap-southeast-1.amazonaws.com. The credentials endpoint is a different prefix and looks like yyyyy.credentials.iot.ap-southeast-1.amazonaws.com.

8. Build the AWS-mode core image

The nucleus image includes Java, the nucleus, Python 3.12 and venv. The component installs its own Python environment, so the core must be able to create a virtual environment. 

docker buildx build \
  --platform linux/arm64 \
  --load \
  -f nucleus/Dockerfile \
  -t edge-platform-nucleus:aws-arm64 .

On Intel, use linux/amd64 and tag it aws-amd64.

9. Start the core with the real identity

docker volume create edge-platform-aws-core-root

docker run -d --init --name edge-platform-aws-core \
  --platform linux/arm64 \
  -v edge-platform-aws-core-root:/greengrass/v2 \
  -v "$PWD/certs/sandbox:/certs:ro" \
  -e GG_MODE=aws \
  -e GG_THING_NAME="$THING" \
  -e GG_CERT_DIR=/certs \
  -e AWS_REGION="$REGION" \
  -e GG_TES_ROLE_ALIAS="$ROLE_ALIAS" \
  -e GG_IOT_DATA_ENDPOINT="$DATA_ENDPOINT" \
  -e GG_IOT_CRED_ENDPOINT="$CRED_ENDPOINT" \
  edge-platform-nucleus:aws-arm64

Check the logs and the cloud status:

docker logs --tail 30 edge-platform-aws-core

aws greengrassv2 list-core-devices \
  --region "$REGION" --profile "$PROFILE"
Expected. Launched Nucleus successfully in the container log, and the core device edge-platform-sandbox-core in status HEALTHY.

If the core is not healthy, stop here and read Part 6. Do not continue with a broken core; every later error will be harder to interpret.

10. Upload and publish the component

The component recipe points at an S3 object. Upload the exact ZIP that the recipe names, then create the immutable component version. 

KEY="${COMPONENT}/${VERSION}/EdgeCollector-${VERSION}.zip"

aws s3 cp \
  "build/component/EdgeCollector-${VERSION}.zip" \
  "s3://${BUCKET}/${KEY}" \
  --profile "$PROFILE" --region "$REGION"

aws greengrassv2 create-component-version \
  --inline-recipe fileb://build/component/recipe.yaml \
  --region "$REGION" --profile "$PROFILE"
Component versions are immutable. If the recipe or artifact changes, bump the version. Never overwrite a published version in place. The proof ended at 1.0.4.

11. Deploy to the core

TARGET="arn:aws:iot:${REGION}:${ACCOUNT_ID}:thing/${THING}"

aws greengrassv2 create-deployment \
  --target-arn "$TARGET" \
  --deployment-name edge-platform-sandbox-collector-1 \
  --components "{\"${COMPONENT}\":{\"componentVersion\":\"${VERSION}\"}}" \
  --deployment-policies '{"failureHandlingPolicy":"ROLLBACK","componentUpdatePolicy":{"action":"NOTIFY_COMPONENTS","timeoutInSeconds":60}}' \
  --region "$REGION" --profile "$PROFILE"

Wait for completion:

aws greengrassv2 list-deployments \
  --target-arn "$TARGET" --history-filter ALL \
  --region "$REGION" --profile "$PROFILE"

aws greengrassv2 list-installed-components \
  --core-device-thing-name "$THING" \
  --region "$REGION" --profile "$PROFILE"
Expected. The deployment reaches COMPLETED (some versions report SUCCEEDED), and the collector appears with lifecycleState: RUNNING.

12. Verify the real message

The simplest way is the AWS IoT console: IoT Core → Test → MQTT test client → subscribe to edge/#. The collector publishes about once per second. 

edge/edge-platform-sandbox-core/plc-line-1/telemetry
{
  "schema_version": "1.0",
  "gateway_id": "edge-platform-sandbox-core",
  "device_id": "plc-line-1",
  "seq": 20,
  "samples": [
    {
      "device_id": "plc-line-1",
      "metric": "temperature",
      "value": 23.5,
      "unit": "degC",
      "quality": "good"
    }
  ]
}

For a terminal observer, create a separate certificate and a read-only policy for client/edge-platform-sandbox-observer, topicfilter/edge/# and topic/edge/*, then: 

mosquitto_sub \
  -h "$DATA_ENDPOINT" -p 8883 \
  --cafile certs/sandbox/AmazonRootCA1.pem \
  --cert certs/sandbox/observer.cert.pem \
  --key certs/sandbox/observer.private.key \
  -i edge-platform-sandbox-observer \
  -t 'edge/#' -C 1 -W 60 -v

13. Teardown — not yet automated

Do not run a blind teardown. Deleting a certificate or role that is still attached to a live core can leave confusing state. The current sandbox is intentionally still live. A repeatable teardown script is a future task; until then, remove in this order and confirm each step.
  1. Stop and remove the local core container and volume.
  2. Create a deployment that removes the collector, or delete the deployment target after the core is stopped.
  3. Delete the component versions (old versions first, latest last).
  4. Detach and delete the observer policy and certificate.
  5. Detach and delete the core policy and certificate.
  6. Delete the role alias, inline role policy and role.
  7. Remove the thing from its group; delete the thing and group.
  8. Empty and delete the S3 bucket (or remove only the component prefix).
  9. Delete CloudWatch log groups created by the test.
  10. Delete local certs/sandbox/ if it is no longer needed.
Why this chapter is long. The AWS path is not one API call. It is a chain of identity, permission and networking pieces. Each piece exists for a reason; Part 6 explains what each failure looked like in practice.
