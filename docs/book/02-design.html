The design: one narrow waist, many protocols

The project is shaped like an hourglass. Many solar-site protocols enter the top, everything narrows into one frozen data shape, and one northbound path carries it to AWS.

The stack, from site to silicon

Site configuration
addresses, names, thresholds
↓
Adapter component
OPC UA · Modbus · MQTT
↓
Frozen contract
Sample / Batch + JSON Schema
↓
Base component set
pipeline · spool · health · publisher
↓
Base image
Ubuntu · Python · nucleus · hardening
Only the bottom layer is an image. Everything above it is a component or configuration.

The rule that follows from this picture is simple: if a change would make two sites need different base images, it belongs above the image, not inside it.

Northbound and southbound

Northbound

Everything toward AWS: the wire format, batching, device identity, mutual TLS, store-and-forward, health, deployment mechanics and logging. It changes rarely and is owned by the base.

Southbound

Everything toward the site: protocols, register maps, byte order, scaling, polling cadence, serial settings and vendor quirks. It changes per site and belongs to adapters and configuration.

The line in the sand. The base owns everything from the data contract northward. The site owns everything south of it. Crossing that line in the wrong direction is how projects end up with one image per customer.

The frozen contract: Sample and Batch

A Sample is one measurement from one metric. A Batch is an ordered group of samples from one device, sent as one northbound message. The batch is per device because the device id is part of the topic, and because a dashboard usually wants one device’s readings together.

What a Sample carries

FieldMeaningExample
device_idThe logical asset the reading belongs to.plc-line-1
metricThe name of the measurement.temperature
valueA number, string or boolean.23.5
tsWhen the reading was observed; always UTC.2026-10-17T12:57:51Z
sourceWhich protocol family produced it.opcua, modbus, mqtt, sim
originWhere inside that protocol it came from.a node id, topic or register
unitOptional engineering unit.degC
qualityWhether the value should be trusted.good, uncertain, bad, stale
tagsSmall string labels for context.{"line": "A"}

Quality is deliberately OPC UA style. A value can exist but be bad. A pipeline that throws away quality information cannot tell “zero” from “unknown”.

The JSON is compact on the wire (no spaces) because AWS IoT Core has a 5 KB tier that this project deliberately stays under.

Topics and identities

There are only two topics in the frozen v1 namespace:

edge/<gateway_id>/<device_id>/telemetry
edge/<gateway_id>/status

The gateway id is also the AWS IoT thing name. It must be safe as a thing name. The device id lives only in a topic level and may contain dots. Both are immutable. Site, tenant and environment belong in the payload or a registry, not in the topic, unless a real routing requirement is proven.

The pipeline: ingest, batch, deliver

The pipeline is deliberately small. Readings enter from a source, wait in a bounded queue, are grouped by device, and are delivered to a sink. The important decisions are in the edges, not in a large framework.

Two flush triggers, and no third

  • A batch is sent when it reaches max_samples.
  • Or when flush_interval_s has elapsed, whichever comes first.
  • Shutdown flushes the buffer once more, so a clean stop does not strand data.

A bounded queue

The queue has queue_max slots. If the sink is slower than the source, the queue eventually fills. The shipped default — and the default in all three configs — is drop_oldest. When full, the oldest queued sample is removed, the newest is retained, and the loss is counted in dropped_queue_full. drop_newest is an explicit opt-in. There is deliberately no “block” policy, because a sensor callback must never stall the whole gateway.

Ordering is the strongest guarantee

Once anything is in the spool, new batches are appended behind it. The replay loop sends oldest first. Nothing overtakes the backlog. This matters more than raw throughput: a dashboard can tolerate a delay, but it cannot easily repair out-of-order history.

The spool: an outbox that survives a power cut

The spool is a SQLite database in WAL mode. It stores the exact JSON payload of each batch, oldest first, and deletes rows after they are delivered.

  • Budget on payload bytes, not file size. SQLite does not return freed pages promptly; a file-size budget would purge forever.
  • Thread-safe. The connection is opened with check_same_thread=False and every operation is serialised behind a lock.
  • Bounded. When the payload budget is exceeded, the oldest batches are dropped first, and the event is logged.
  • Crash-safe. WAL and synchronous=NORMAL make it survive an ordinary power loss without a separate database service.

Sinks: one transport at a time

A sink owns exactly one way of sending a batch. The pipeline does not care which one it is. A sink raises SinkUnavailable when the transport is down, and the pipeline decides whether to spool or drop.

SinkUseNotes
logLocal development and tests.Writes one line per batch; no network.
mqttLocal broker or direct IoT Core over mTLS.Uses paho; certificates are configured explicitly.
greengrassProduction path through the Greengrass nucleus.No AWS keys in the component; publishes over the local IPC socket.

The Greengrass sink is not a network client. It talks to the nucleus over a Unix socket. The nucleus owns the device certificate, the AWS IoT connection and its offline queue. If the nucleus is down, the sink reports unavailable and the collector spools.

Health: three tiny endpoints

EndpointMeaning
/healthz“The process is alive.” Always 200 while the server runs.
/readyz“Every enabled source is connected.” 200 when ready, 503 when not.
/statsJSON counters: accepted, built, sent, spooled, replayed, dropped, sink health, source health.

This is deliberately built on the Python standard library, not a web framework. On a device that may not be touched for years, fewer dependencies means fewer security patches and fewer surprises.

The image and the component

The image is the bottom layer: a pinned Ubuntu 24.04 userland, Python 3.12 in a virtual environment, a non-root user, a health check and the collector installed in that environment. It does not contain site-specific point maps.

The component is above the image: a ZIP of the collector wheel plus its dependencies, a recipe that tells Greengrass how to install and run it, and an access-control policy. Site-specific settings are component configuration, not a new image.

Base image

+
Collector component

+

The image is reused. The component is versioned. The site config changes per deployment.

Why NoContainer?

Greengrass components can run in Docker or as ordinary processes. This project uses process mode (NoContainer) because the collector is a normal Linux process and the gateway should not need a Docker daemon inside the device. It keeps the image smaller and the failure modes simpler.

Why the component namespace matters

Components live under io.github.doudouba0309.EdgePlatform. That namespace is a sandbox placeholder tied to the current Git owner, not a technical dependency. Client and site names belong in configuration, thing groups and deployment names, not in component names. Before a client deploy, change to a client-owned namespace as a new component family and version; see Environment Portability.

Security design, in one page

  • No long-lived AWS keys in the component. The nucleus owns the device certificate and obtains temporary credentials through the token exchange service.
  • One device identity. The certificate is attached to a thing; the IoT policy limits the exact client id and topics.
  • Least privilege, with explicit exceptions. The core needs MQTT rights, Greengrass control-plane rights and permission to assume the TES role. The TES role needs S3 read and logging.
  • No secrets in git. A secret guard checks tracked paths and contents; a pre-commit hook and a separate CI workflow enforce it.
  • No root AWS user for daily work. The sandbox uses a named admin profile, MFA and a budget.

The design in one sentence. Normalise everything into one batch, protect it with a bounded queue and a disk spool, and hand it to a local postmaster that owns the cloud identity — while keeping site-specific protocol work out of the image.
