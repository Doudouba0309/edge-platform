Edge Platform · Operations guide

Set up an AWS sandbox

A calm, step-by-step path from a brand-new AWS account to a disposable Greengrass test environment. No production account, no root access keys, no guesswork.

About 25–40 minutes Suggested budget: $10 Region: ap-southeast-1 Sandbox only

What you are creating, in plain language

AWS gives every job its own named object. This guide creates a safe, disposable set of them:

AccountThe client’s container. Root is emergency-only.
Admin identityYour named daily login, with MFA, not root.
Thing + certificateThe gateway’s name and passport.
PolicyExactly which topics the passport may use.
RoleA temporary badge for the nucleus to read the component ZIP.
BucketPrivate storage for the component artifact.

The sequence matters: the account and identity come first; the thing and certificate next; the policy and role after that; the bucket last. The Greengrass core ties them together.

Do not use production. This is a sandbox guide. It creates billable resources and a gateway identity. Use a dedicated account and a budget alarm.

What you are building

You are creating a small, isolated AWS account that the project can use to provision a test Greengrass core, publish a component, deploy it, and verify telemetry. The account is disposable. Nothing here should contain production devices, customer data or shared company resources.

AccountA dedicated, non-production AWS account.
GuardrailsMFA on root and admin, plus a small budget alarm.
AccessOne CLI profile the agent can use; no secrets in chat.
Use the right account. Do not follow this guide in a production account. If your organisation provides a sandbox account, use that and skip step 1.

What you need

  • An email address you can access (ideally dedicated to this sandbox).
  • A password manager, a phone for verification, and a payment card for AWS.
  • An authenticator app for MFA.
  • A terminal on this Mac.

At a glance

  • Create the account and choose the Basic support plan.
  • Turn on root MFA. Do not create root access keys.
  • Create a $10 monthly budget alert.
  • Create a dedicated admin identity with MFA.
  • Install the AWS CLI and configure the edge-sandbox profile.
  • Verify IoT, Greengrass and S3 access.
  • Create one private S3 bucket.
  • Send the agent the account ID, region, profile name and bucket name.
1
Account

Create the AWS account

10–20 minutes, including email and identity verification.

  1. Open portal.aws.amazon.com/billing/signup.
  2. Enter the sandbox email address and a strong password. Use a password manager.
  3. Choose an account name such as edge-platform-sandbox.
  4. Complete contact information, payment method and identity verification. AWS may place a small temporary charge to verify the card.
  5. Choose the Basic support plan; it is free and sufficient for a sandbox.
  6. Wait for the account activation email, then sign in at console.aws.amazon.com.
Region. Use ap-southeast-1 (Singapore) for this project unless you have a reason to use another region. Keep every resource in that region.
You can sign in to the AWS Management Console as the root user.
2
Security

Secure the root user

5 minutes.

The root user is the account owner. You should use it only for account-level tasks.

  1. Sign in to the console as the root user.
  2. Open the account menu (top right) → Security credentials.
  3. Under Multi-factor authentication (MFA), assign an authenticator app.
  4. Store the recovery codes in your password manager.
  5. Do not create a root access key. If one already exists, delete it.
Never use the root user for daily work. No root access keys, no root credentials in scripts, no root credentials in chat or in this repository.
Root MFA is active and there are no root access keys.
3
Cost control

Set a budget alarm

3 minutes.

  1. Open Billing and Cost Management → Budgets.
  2. Choose Create budget → Monthly cost budget.
  3. Name it edge-platform-sandbox-monthly.
  4. Set the amount to $10 (or a limit you are comfortable with).
  5. Add your email as an alert recipient, for example at 80% of the budget.
  6. Create the budget.
A budget is an alarm, not a hard cap. AWS will email you when spending crosses the threshold, but it will not automatically stop resources. Teardown at the end still matters.
The budget appears in Billing → Budgets and your email is subscribed.
4
Identity

Create your daily admin access

5–10 minutes.

Stop using root. Create a separate admin identity for the console and CLI. For a dedicated sandbox, the simple path is an IAM user with MFA. A stricter, longer-term option is IAM Identity Center (SSO).

Option A — IAM admin user (simplest for a throwaway sandbox)

Before you sign out of root: note your 12-digit account ID. The IAM user sign-in page asks for the account ID (or an account alias). While signed in as root, click the account name in the top-right corner and copy the Account ID. Optionally create an alias in IAM → Dashboard → AWS Account; then you can sign in at https://edge-platform-sandbox.signin.aws.amazon.com/console. If you are already signed out, choose Forgot account ID? on the sign-in page and enter the root email.
  1. Open IAM → Users → Create user.
  2. Name it edge-platform-admin.
  3. Check Provide user access to the AWS Management Console, choose a custom password, and require a password reset on first sign-in.
  4. On the permissions step, choose Attach policies directly and select AdministratorAccess.
  5. Create the user. Sign out of root, choose IAM user on the sign-in page, enter your account ID or alias, then sign in as edge-platform-admin.
  6. In the new user's Security credentials, enable MFA with an authenticator app.
  7. Still in Security credentials, choose Create access key → Command Line Interface (CLI) and download the CSV.
AdministratorAccess is acceptable only because this is a dedicated sandbox. Do not attach it to a shared account. Delete the access key when the sandbox is finished. Never paste the secret key into chat.
Option B — IAM Identity Center / SSO (better, no long-lived keys)

If you prefer SSO, open IAM Identity Center, enable it, create a user for yourself, create a permission set with AdministratorAccess, and assign it to the sandbox account. Enabling Identity Center in a standalone account creates an AWS Organization, which is fine for a sandbox.

Then use the access portal URL it gives you (it looks like https://d-xxxxxxxxxx.awsapps.com/start) when configuring the CLI in step 6. This avoids creating an IAM access key.

You can sign in as an admin user, MFA is active, and you have a CLI access key (Option A) or an SSO start URL (Option B).
5
Tooling

Install the AWS CLI

3 minutes.

On macOS, Homebrew is the quickest route if you already use it:

brew install awscli
aws --version

Otherwise use the official package:

curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o "AWSCLIV2.pkg"
sudo installer -pkg AWSCLIV2.pkg -target /
aws --version
aws --version prints AWS CLI 2.x.
6
Access

Configure the sandbox profile

3–5 minutes.

With an IAM access key (Option A)

aws configure --profile edge-sandbox

Enter the values from the CSV you downloaded:

  • AWS Access Key ID and Secret Access Key
  • Default region name: ap-southeast-1
  • Default output format: json

With IAM Identity Center (Option B)

aws configure sso --profile edge-sandbox
aws sso login --profile edge-sandbox

Use the access portal URL and region shown in IAM Identity Center. Choose the sandbox account and the admin permission set when prompted. Set the CLI region to ap-southeast-1.

Verify the identity the CLI will use:

aws sts get-caller-identity --profile edge-sandbox
The profile name is the hand-off. The agent only needs the profile name edge-sandbox. It does not need your access key or password.
get-caller-identity returns the sandbox account ID and an admin role/user.
7
Readiness

Verify the required services

2 minutes.

These commands should succeed. Empty lists are fine; an error is not.

aws iot describe-endpoint \
  --endpoint-type iot:Data-ATS \
  --region ap-southeast-1 \
  --profile edge-sandbox

aws greengrassv2 list-components \
  --region ap-southeast-1 \
  --profile edge-sandbox

aws s3api list-buckets --profile edge-sandbox

The IoT command prints an endpoint such as xxxxxxxxxxxx-ats.iot.ap-southeast-1.amazonaws.com. That confirms IoT Core is reachable in the chosen region.

If you get AccessDenied: check the profile name, the region, and whether the identity really has admin permissions. Do not widen permissions in a shared account; use the dedicated sandbox.
IoT Core, Greengrass V2 and S3 commands all return successfully.
8
Storage

Create the sandbox bucket

2 minutes.

Greengrass component artifacts need an S3 bucket. The name must be globally unique. Use the account ID in the name: 

ACCOUNT_ID="$(aws sts get-caller-identity \
  --profile edge-sandbox \
  --query Account --output text)"

BUCKET="edge-platform-sandbox-${ACCOUNT_ID}-ap-southeast-1"

aws s3api create-bucket \
  --bucket "$BUCKET" \
  --region ap-southeast-1 \
  --create-bucket-configuration LocationConstraint=ap-southeast-1 \
  --profile edge-sandbox

aws s3api put-public-access-block \
  --bucket "$BUCKET" \
  --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile edge-sandbox

echo "$BUCKET"
aws s3 ls --profile edge-sandbox

If the bucket name is already taken, add a short suffix such as -01. Keep the bucket private.

The bucket exists, public access is blocked, and aws s3 ls shows it.
9
Hand-off

Send the agent four facts

1 minute.

Account ID: 123456789012
Region: ap-southeast-1
Profile: edge-sandbox
Bucket: edge-platform-sandbox-123456789012-ap-southeast-1
Confirmed non-production: yes
Do not send: root password, IAM secret access key, MFA codes, or a session token. The agent only needs the profile name. Never paste secrets into chat.

What the agent will do

  1. Verify the identity and region with get-caller-identity.
  2. Provision a test thing, certificate, IoT policy, IAM role and role alias.
  3. Bootstrap the nucleus and make greengrass-cli available.
  4. Publish the collector component to the sandbox bucket.
  5. Deploy it to the test core and verify telemetry.
  6. Tear everything down and report what was deleted.
The agent can run aws sts get-caller-identity --profile edge-sandbox successfully.
10
Cleanup

Tear it down

5–10 minutes.

Either the agent performs this or you do it manually. Delete in this order:

  1. Cancel/delete Greengrass deployments.
  2. Delete the published component and its versions.
  3. Delete the test thing and thing group.
  4. Deactivate and delete the test certificate.
  5. Detach and delete the test IoT policy.
  6. Delete the IAM role alias, inline policies and role.
  7. Empty and delete the S3 bucket.
  8. Delete the CloudWatch log groups created during the test.
  9. Delete the IAM access key (Option A) if the sandbox is finished.
  10. Optionally close the AWS account if it was created only for this test.
Find resources by tag. The agent tags resources with project=edge-platform and environment=sandbox. Use those tags to find leftovers.
The sandbox has no running deployments or billable test resources, and the S3 bucket is empty.

What comes next — and what not to create

Do not create a second Greengrass component for “IPC”. The Greengrass IPC sink is code inside the collector, not a separate AWS resource. There is exactly one component to publish: io.github.doudouba0309.EdgePlatform.Collector.

The collector's Greengrass IPC sink is implemented and unit-tested. It is part of the same component, so it can ask the nucleus to publish to IoT Core. It is not an AWS component, an IoT thing, or a separate deployment.

The collector is now packaged with make component: a universal Linux wheelhouse, a two-architecture recipe and the rendered IoT policy. Publishing and deploying those artifacts is the remaining AWS step.

What you should do in AWS right now: nothing. The account, admin identity, region and private bucket are enough. Do not create an IoT thing, certificate, role or Greengrass component by hand unless you specifically want to manage those resources yourself.
You understand that there is one collector component and no separate IPC component to create.

Appendix C — troubleshooting

“SSO session expired”

Run aws sso login --profile edge-sandbox and retry.

“AccessDenied”

  • Confirm --profile edge-sandbox is present.
  • Confirm --region ap-southeast-1 is correct.
  • Confirm the identity has the required policy and no organisation SCP blocks it.
  • Check that you are not accidentally using the root or another account.

“BucketAlreadyExists”

S3 bucket names are globally unique. Add a suffix to the bucket name.

“Not authorized to perform iot:DescribeEndpoint”

The identity is missing IoT permissions, or the region is not enabled for your account.

The budget alarm did not stop spending

Budgets are notifications, not hard limits. Teardown is still required.

Account verification is taking a long time

AWS may need additional identity or payment verification. Check the signup email and the console banner. Do not create duplicate accounts.

“I lost the root MFA device”

Use the recovery codes you saved. If those are lost, follow the AWS account recovery process; this is intentionally difficult.
