One Base, Many Protocols

Historical design argument. Current state, decisions and operating guidance live in the handbook, the decision register and the release-readiness checklist. This document is kept for the original rationale, not as the current plan.

A single, slowly-changing base for edge gateways, with the field side left open — so a new site is a configuration and a small adapter component, not a forked product.

Tier 1: arm64 + x86_64 only · built and smoke-tested in CI on every commit

If you read only one thing

Freeze the northbound (device identity, telemetry contract, store-and-forward, health, deployment) and leave the southbound open. Put the seam at a versioned data contract, not at a protocol list. Deliver site specifics as Greengrass components and configuration, never as a bespoke image — because a bespoke image per site turns one security patch into N rebuilds and N re-verifications.

Most field protocols need no code at all: a Modbus register map, an OPC UA node list, an MQTT topic path and a BACnet object list are all declarative. Ship the declarative engine in the base and reserve generated code for genuinely novel protocols. That single choice is what makes the rest — including agent-driven delivery — tractable.

The shape of the problem

Edge deployments vary along two independent axes. Conflating them is what produces the unmaintainable "universal gateway".

The two axes, and why only one of them should be standardised
AxisWhat variesVerdict
Northbound
freeze		 Nothing meaningful. Device identity, mutual TLS, telemetry envelope, batching, store-and-forward, health, deployment mechanics, logging. Identical in almost every deployment. Standardise once, version carefully, and never let a site fork it.
Southbound
leave open		 Protocol, device quirks, register layout, byte and word order, scaling, polling cadence, serial framing, vendor dialects, connectivity. Combinatorial. Every attempt to unify it ends as a configuration swamp. Treat it as an extension point with a contract, not as a feature list.

The one-line rule

The base owns everything from the data contract northward. The site owns everything south of it. If a change would make two sites' base images differ, it belongs south of the line.

One base, four layers

The design is a stack, and the important property is that only the bottom layer is an image. Everything above it is a Greengrass component or plain configuration, which is what makes updates cheap.

What lives where, and how often each layer moves
LayerContains Packaged asChangesWhy it is here
Site configuration Point maps, tag names, host addresses, deadbands, thresholds ConfigurationPer site, anytime No artifact, no rebuild, no review burden — a config change is a deployment, and it is reversible.
Adapter component Declarative engine bindings, or a code adapter for a custom protocol Greengrass componentPer deployment This is the "open front". It can be updated independently of the base, which keeps the patch surface small.
Base component set Northbound publisher, spool, health, adapter engine, config loader Greengrass componentsVersioned releases Shared by every site, so one fix reaches the whole fleet through a single deployment.
Base image OS, Python runtime, Greengrass nucleus, provisioning, hardening OCI image / disk imageRarely Only hardware and firmware differences force a new image: NIC or modem drivers, kernel modules, architecture.

The tempting mistake

Building "one image per site" because it feels simpler. It is simpler for the first deployment and strictly worse from the second onward: a glibc or OpenSSL advisory becomes N rebuilds, N re-verifications and N opportunities to ship something subtly different. Keep the image boring and identical across sites; let the site be a component plus data.

The seam: a data contract, not a protocol list

The adapter layer has exactly one obligation: turn whatever it speaks into the canonical Sample and hand batches of them northward. Nothing else in the system needs to know where a value came from — not the batching logic, not the spool, not the transport. 

// The frozen contract. Versioned, schema-checked, and the only thing
// both sides must agree on.
{
  "schema_version": "1.0",
  "gateway_id": "gw-factory-7",
  "device_id": "plc-line-1",
  "seq": 482,
  "produced_at": "2026-10-16T10:39:45.436Z",
  "samples": [
    {
      "device_id": "plc-line-1",
      "metric": "temperature",
      "value": 25.221,
      "ts": "2026-10-16T10:39:45.101Z",
      "source": "opcua",
      "origin": "ns=2;s=Line1.Temperature",
      "unit": "degC",
      "quality": "good",
      "tags": { "line": "1" }
    }
  ]
}

Why a schema and not a document

The contract is published as JSON Schema, and a test fails the build if the committed schema drifts from the code that produces it. That makes it machine-checkable by three consumers at once: the CI gate, downstream services (IoT rules, Lambda, a data platform), and an agent that has to decide whether its own output is valid before shipping it.

Two properties of this contract matter more than the rest, because getting them wrong produces the failure mode that edge systems are worst at — silently wrong data, which flows into a historian and is noticed months later:

  • Time is unambiguous. Every timestamp is timezone-aware UTC. A naive input is treated as UTC rather than guessed at.
  • Quality is carried, not inferred. A bad OPC UA status becomes quality: "bad" on the wire. A stale value is marked stale. Nothing is silently upgraded to good.

Declarative first, code as the exception

This is the highest-leverage decision in the proposal. Most industrial protocols are not programming problems; they are mapping problems.

ProtocolWhat a site actually specifiesCovered by the declarative engine?
OPC UAEndpoint, node ids, scaling, deadband, security policyYes
Modbus TCP / RTURegister map, data types, word and byte order, scaling, unit idYes
MQTTTopic filter, JSON field paths, device identifierYes
BACnet/IPDevice instance, object type and instance, propertyYes
Vendor binary / serial framingA proprietary frame layout, checksum, handshakeNo — code adapter
CAN / J1939, proprietary busesSignal database, bus arbitration, custom decodingNo — code adapter

A declarative point map is worth more than it looks: it is reviewable by a controls engineer who does not read Python, it diffs cleanly, it is trivially validated, and — critically — an agent cannot invent a plausible-looking bug in it as easily as it can in generated code.

source: opcua
connection:

    node: "ns=2;s=Line1.Temperature"
    unit: degC

Modbus, declaratively

source: modbus_tcp
connection: { host: 10.0.4.21, port: 502, unit: 1 }
poll_interval_s: 5
points:
  - metric: tank_level
    register: 40011        # holding, 1-based
    type: uint16
    scale: 0.1             # tenths of mm -> mm
    unit: mm
  - metric: flow_rate
    register: 40012
    type: float32
    word_order: big
    byte_order: big

Where silent-wrong data actually comes from

Not crashes — conventions. A 1-based register 40011 read as 0-based; a float32 with swapped word order; an unsigned register that is really signed; a scaling factor off by a factor of ten; a stale value presented as fresh. Every one of these produces plausible numbers. The conformance suite exists to catch exactly this class of error, which is why it is a required artifact and not a nice-to-have.

The adapter contract and its conformance suite

An adapter is not "done" when it compiles and moves data once. It is done when it passes a conformance suite against a surrogate of the real device. Make the surrogate a required deliverable, because verification, not generation, is the bottleneck.

Required artifacts for every adapter — a code adapter and a declarative map alike
ArtifactPurpose
Adapter or point mapThe thing itself: declarative points, or a Source implementation that emits Samples.
SurrogateA simulator built from the register map, or a replayed capture of real device traffic. Without one the adapter is unverifiable, and an unverifiable adapter on a plant floor is worse than none.
FixtureKnown-good input and its expected canonical output, checked into the repository. This is what makes regressions detectable and review possible.
Conformance reportThe machine-readable result of running the suite. Reviewed by a human; attached to the change.
Resource budgetMeasured memory and CPU on the smallest Tier 1 target, with a declared ceiling.

What the conformance suite must check

CheckWhy it is in the suite
Schema conformanceOutput validates against the frozen JSON Schema. Non-negotiable and cheap.
Scaling round-tripRaw count and engineering value agree through the declared factor and offset, property-tested across the range.
Word and byte orderPinned by a golden fixture from the vendor document. This is the single most common silent error.
Signedness and boundsValues outside a declared domain are flagged, not passed through as truth.
Timestamp sanityUTC, monotonic per metric, not implausibly far in the future.
Quality propagationA device-reported bad or stale status reaches the wire as bad or stale.
Reconnect and no-lossKilling the surrogate mid-run must not crash the collector, and buffered data must replay rather than vanish.
Resource ceilingMeasured RSS and CPU stay inside the budget on the smallest Tier 1 target.
DeterminismThe same fixture yields byte-identical payloads, timestamps aside.

Tier 1: two architectures, gated in CI

Multi-architecture support is a cost, not a feature. Two targets, explicitly supported, beats six half-supported — and an explicit out-of-scope list is what stops the support matrix growing by accident.

TierPlatformsCommitment
Tier 1 arm64 (aarch64)
x86_64 (amd64)		 Built, smoke-tested and published on every commit. A failure in either blocks the change.
Tier 2 armv7 (32-bit) Not built by default. Admitted only with a named deployment, a memory budget, and its own CI job. Slower, memory-constrained, and lacks some of the base's convenience.
Out of scope armv6, RISC-V, musl/Alpine Not supported. The escape hatch is a bespoke image, owned by that deployment, outside this pipeline.

The per-commit pipeline

  1. BuildBoth arches via buildx. Base digest pinned; dependency lock frozen.
  2. SBOM + scanSoftware bill of materials produced and vulnerability-scanned.
  3. Boot smokeImage boots on both arches; nucleus and health endpoint come up.
  4. ConformanceSuite runs against fixtures; schema and determinism checked.
  5. PublishReference by digest, never by floating tag. Regenerate and diff.
  6. Human gateWrites to field devices, and any adapter change, need review.

What "smoke-tested" means, precisely

A definition, so it cannot quietly decay into "the build succeeded":

  • the image boots on both Tier 1 architectures;
  • the collector reaches a ready state with a synthetic source, and /healthz returns 200;
  • one batch is published over mutually authenticated TLS to a local broker, and arrives on the production topic with a schema-valid payload;
  • the process exits cleanly on SIGTERM, flushing its buffer;
  • measured memory stays inside the declared ceiling.

This is not hypothetical scaffolding: the mutual-TLS harness already exists in the repository and runs the real sink against a certificate-requiring broker.

Updates: the decision that constrains everything else

Before generating anything, decide how a fix reaches a device. The answer determines the artifact layout, and retrofitting it later is expensive.

Recommended split: only hardware and firmware force an image
What changedMechanismReachesCost per event
OS, glibc, OpenSSL, runtime New base image digest, OTA or reflash Every site One rebuild, two architectures, one smoke test — then a fleet rollout.
Northbound, spool, engine Base component version, Greengrass deployment Every site One publish, one deployment. No image work at all.
A protocol adapter Adapter component version Only affected sites Localised, independently reversible.
Registers, tags, thresholds Configuration on the thing or group One site No artifact. Reversible in seconds.

Still open

Confirm this split, or choose the alternative: immutable per-site images with A/B partitions, which simplifies rollback at the device but makes every OS-level fix a fleet-wide rebuild. The recommendation here is the table above; the cost difference compounds over years, not weeks.

The agent factory

The per-deployment work is bounded, repetitive and verifiable: read a register map, produce a mapping, test it against a surrogate, package it. That is exactly the profile where agents help most — provided the surrounding structure makes wrong output detectable.

ConcernHow it is scopedThe rule that keeps it honest
Context Layered: invariant (the contract) → reusable (adapter kit, protocol playbooks) → site (register map, captures) → this task. Load only the layers a task needs. Injecting the whole repository is how a context window gets spent on irrelevant detail.
Skills Procedures, versioned in the repository, contract-tested like code. A skill without a verification command is a liability. Every skill ends in something that returns pass or fail.
Memory Facts as data: register maps, addresses, capture locations, known device quirks. Facts carry an owner, an expiry and the evidence that produced them. Technique belongs in skills. Credentials are never stored here.
Subagents Defined by artifact contract: input, output artifact, verification command, refusal condition. An agent that will not refuse is an agent that will guess. "No capture and no simulator" must produce a refusal, not a register map.

The failure that matters most

An invented register map. A model can produce a completely plausible point map that is wrong in one field, and nothing downstream will complain — the numbers look fine. The rule is therefore absolute: a point map originates from a vendor document, a captured trace, or a human controls engineer. Never from inference.

A new deployment, end to end

  1. IntakeHuman: site, hardware, protocol, tag list, plus the register document or a capture.
  2. DecideAgent: does a declarative map cover it? Prefer yes. Escalate to code only when it does not.
  3. SurrogateAgent: build a simulator from the map, or replay the capture.
  4. ConformAgent: run the suite. Produce the report. Refuse if any check fails.
  5. ProposeAgent: open a change containing adapter, fixture, report and budget. Regenerate and diff.
  6. ReviewHuman: read the diff, the conformance report and the resource numbers. Merge.
  7. BuildCI: both architectures, SBOM, boot smoke test, publish by digest.
  8. Roll outAgent: deployment to the site's thing group, watching for completion and rollback.
  9. OperateWrites to a PLC always need a human signature. Read-only telemetry may be autonomous.

Why "regenerate and diff" is the review mechanism

If generation is deterministic — pinned base digest, locked dependencies, sorted output — then reviewing a change means reading a diff, not auditing a generated tree. That is the difference between a review that actually happens and one that is rubber-stamped.

Safety, security, provenance

ConcernPosition
Device credentialsFleet provisioning or short-lived, automatically rotated credentials. An agent never handles a long-lived private key, and no key is ever baked into an image.
Least privilegeOne IoT policy per thing, scoped to that gateway's own topic prefix. A compromised gateway cannot forge another's data.
Write pathsRead-only telemetry can be autonomous. Anything that writes to a PLC — setpoints, commands, mode changes — requires a human decision, regardless of agent confidence.
ProvenanceEvery published artifact records the base digest, the skill versions and the agent run that produced it. Without this a generated deployment cannot be audited or rebuilt.
Regulated sitesWhere a customer requires one certified artifact, declarative configuration is what makes that survivable: the same certified image, different point maps.

Non-goals for the first version

  • Universal protocol coverage. Two or three protocols done really well, with the conformance suite behind them, beats a dozen partial integrations.
  • armv7, armv6 and RISC-V. Explicitly out of the Tier 1 pipeline.
  • Control and writes. Telemetry out first. Control is a safety engineering problem, not a data engineering one.
  • Per-site images as the default. Only hardware or firmware justifies a distinct image.
  • Autonomous register-map inference. Never, at any phase.

What I need from you

Decisions

  1. Update strategy. Confirm the component-first split, or choose immutable per-site images with A/B partitions. This shapes the artifact layout.
  2. First protocols. Which two or three carry the first real deployments? Modbus TCP plus OPC UA is the usual answer, and it makes Phase 1 concrete.
  3. Surrogate source. For each first protocol, where does test data come from — a lab device, a customer capture, or a simulator we build from the document? Phase 2 depends on this more than on any code.
  4. Write policy. Read-only for the first version, or is a write path required early? It changes the review and safety model.
  5. Review owner. Who signs off an adapter change and a conformance report — a controls engineer, a platform engineer, or both?

Proposal for discussion. It reflects the decisions taken so far — Tier 1 restricted to arm64 and x86_64 with per-commit CI, one base design, an open field side — and deliberately states what is not being built as clearly as what is.
